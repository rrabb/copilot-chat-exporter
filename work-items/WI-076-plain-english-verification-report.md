# WI-076 Plain-English verification report

## At a glance

- **Goal:** explain verification results in a short, newcomer-friendly Markdown sidecar.
- **Trigger:** `--verify` creates the sidecar. `--explain` creates it for an ordinary export.
- **Failure policy:** successful and failed verification both create a sidecar.
- **Reference:** `temp-tool-output/261118-EXPORTS/cc-exporter-results-explanation.md`.
- **Design rule:** explain the same structured results used by the console. Don't parse console text a second time.
- **Status 261124:** the dev accepted v4 on 261123. The feature and tracking are committed. This item is complete.
- **Next:** none. Public regression fixtures belong to [WI-078](WI-078-verification-report-fixtures.md).
- **Related:** [WI-077](WI-077-ai-verification-diagnostics.md) owns AI repair diagnostics and exact-sample privacy. [WI-078](WI-078-verification-report-fixtures.md) owns reusable public report fixtures.
- **Reference guide:** [Verification output guide](../docs/VERIFICATION.md) maps every console warning and failure family to plain English.
- **Console-only case:** `--verify <session>` explains the in-memory check in the console and writes no sidecar.

## Original goal

The console report is useful to maintainers, but new users need plain explanations for:

- `present`, `partial`, and `absent` content
- order and repeated-occurrence checks
- intentional exclusions
- unsupported SDK records
- source, usage, parser, and image warnings
- failed verification and kept `.verify-failed.md` files

The attached report explains these ideas well. This item adapts that style into a deterministic report generated by the exporter.

The sidecar must add explanation without changing verification results. It must not turn a warning into a pass or make an incomplete check look complete.

## Done when

- `--verify` writes or prints the explanation in each Local and SDK mode.
- `--explain` writes the report for a normal export.
- Pass, warning, content-loss and verifier-exception cases have focused tests.
- Sidecar collisions keep older files.
- `--json` still prints one machine-readable document.
- README, SPEC and changelog match the behavior.
- Full verification and build pass.
- The dev reviews the clean and failed samples and accepts or requests changes.

## Recommended report structure

1. **Header and verdict**
   - Export succeeded, verification failed, or export failed before verification.
   - Name the actual archive and companion directory.
   - Link the failure log when one exists.

2. **What happened**
   - Say in one paragraph whether the archive is verified.
   - For a failed run, say which checks failed and which checks still passed.
   - Keep the older `.verify-failed.md` file as separate historical evidence.

3. **Checks at a glance**

   | Check | Plain result |
   | --- | --- |
   | Recorded text | All recognized, eligible pieces found |
   | Order | Required ordered pieces stayed in sequence |
   | Repeats | Required repeated occurrences were kept |
   | Images | Recorded image bytes matched linked companions |
   | Markdown | Turn and section structure parsed correctly |
   | Questions | Every recorded question was read, or named warnings remain |

4. **Intentional exclusions**
   - Explain each counted category and why it is noise for review.
   - State that source session data wasn't changed or deleted.
   - Avoid presenting event counts as visible user actions.

5. **Warnings and limits**
   - Separate unknown event types from supported events with unknown fields.
   - Explain that `type:unsupported` is a payload-format warning, not a failed tool call.
   - Translate source parse, schema, question, usage and companion warnings.
   - Keep the original machine-readable name in a code span.

6. **What passing doesn't prove**
   - Layer D covers recognized, eligible text.
   - A present match isn't proof of ideal placement in every ambiguous case.
   - Image hash checks don't validate image meaning.
   - Parser success doesn't prove every source field is understood.

7. **Next useful action**
   - `none` when the result is clean.
   - `inspect <path>` for a kept failed archive.
   - `rerun --strict` when schema warnings remain.
   - `report this drift` for unknown formats.

8. **Reproduction details**
   - Session selector, source hash, exporter version, command mode and verification time.
   - Keep secrets out. Apply the same redaction policy as other generated Markdown.

## `Parse warning` review

The current `- Parse warning:` line in `Export Provenance` is too broad.

Today the `session.errors` list can include:

- malformed Local journal JSON
- unsupported usage receipts
- invalid cumulative usage totals
- other source warnings added by parsers

Not every item is a Markdown parse warning. A new user may think the exported file is malformed.

Recommended change:

1. Keep the warning line for quick in-archive visibility.
2. Rename it to `Export warning` in the implementation that follows this work.
3. Add a warning code or category when the parser owns one.
4. Link from the warning to the explanation sidecar section.
5. Explain the effect in plain language:
   - content skipped
   - content kept with unknown details
   - verification made strict-fail
   - count only

The sidecar must keep the distinction between:

- source parse warning
- exported Markdown parser result
- verification failure
- schema-drift warning

## Original plan, implemented 261119

1. **Define a report model.**
   - Keep result values, categories, counts, file paths and failure states in a typed object.
   - Make console, JSON and sidecar reporting consume the model where practical.

2. **Define explanations as data.**
   - Map known omission, drift, parser and verification categories to short explanations.
   - Keep unknown category fallbacks honest and visible.

3. **Add sidecar naming and lifecycle rules.**
   - Derive the name from the published archive.
   - Handle normal, collision, `--overwrite`, and `.verify-failed` names.
   - Don't delete an older failed sidecar.

4. **Render the report.**
   - Start with the attached report's sequence and plain tables.
   - Add links to the archive, companions, and failure log.
   - Keep machine identifiers available without making them the main story.

5. **Wire the CLI.**
   - Generate automatically with `--verify`.
   - Support `--explain` on ordinary exports.
   - Print the sidecar path in the console.

6. **Add cross-links.**
   - Add a short verification-summary line near `Export Provenance`.
   - Link from schema and parse warnings to the sidecar.
   - Don't duplicate the complete sidecar inside the archive.

7. **Test edge cases.**
   - Successful SDK verification
   - Failed Layer D verification
   - Local verification with parse warnings
   - Schema drift without content loss
   - Missing parser in normal and strict modes
   - Collision-resolved failed and successful filenames
   - Redaction and path handling

8. **Update docs and tracking.**
   - README command and output names
   - SPEC verification report semantics
   - CHANGELOG user-visible feature
   - WI-076 evidence and acceptance

## Risks and limits

| Risk | Mitigation |
| --- | --- |
| Two reporters drift apart | Build both from one structured report |
| The report overstates success | Use "checked" and "recognized" limits in every summary |
| Private data appears twice | Reuse archive redaction and don't copy raw payloads by default |
| The sidecar becomes stale | Tie it to the exact archive and source hash |
| Failed files clutter output folders | Opt in for ordinary exports and keep one sidecar per published archive |
| Explanation text becomes promotional | Report evidence and limits, not a losslessness claim |
| Machine names remain hard to read | Show plain language first, then the exact code in a compact line |

#### Specific wording changes

| Current v2 text | Better new-user wording |
| --- | --- |
| `Recorded text` | **Content check**: did the archive keep the recorded text? |
| `Layer D` | The independent check that compares source text with the saved archive |
| `Unhandled event types` | Copilot saved a new record type this exporter doesn't know yet |
| `Unsupported payload variants` | This record type is known, but one or more fields changed |
| `Source-ordered message text` | Did the conversation text stay in the same order? |
| `Repeated-text groups` | When the same phrase appeared more than once, did every copy survive? |
| `Fix the 874 content problems` | Inspect the 874 verification failures. Some can come from the exporter or verifier, not the user's chat |
| Five identical affected locations | Say five examples were shown and 869 more failures remain, without repeating the same request line five times |

#### Recommendation

Keep v2's evidence and complete coverage. Add a compact plain-language diagnosis at the top. Collapse the raw-detail tables. Don't remove detail to make it look simpler.

The target is:

- about 250-400 words visible before the first collapsed section
- complete raw details still present
- no unexplained project term in the visible summary
- one clear sentence for each failed or warning condition
- no default instruction that tells the user to fix every verifier failure

The report links only an actual generated log. Verification-result failures and verifier exceptions write logs. General command, capture or destination errors may fail before a verification log exists.

## Follow-up review 261124

WI-076's focused tests already cover the renderer, Local and SDK branches, warning/failure wording, exception reports and collision-safe writes. A second renderer test suite would add cost without much confidence.

The useful follow-up isn't more WI-076 implementation. It's a small public fixture pair owned by [WI-078](WI-078-verification-report-fixtures.md):

| Need | Reuse | Don't duplicate |
| --- | --- | --- |
| Stable reader-facing output | Two invented `VerificationExplanationInput` records and exact expected sidecars | Private v1-v4 review bundles |
| Regression confidence | Render both reports directly through the existing explanation renderer | Rebuild report logic in a fixture generator |
| CLI evidence | Existing focused CLI and collision tests | Full real-CLI fixtures for each report |
| Diagnostic coverage | Synthetic events and `scripts/lib/cli-sandbox.mjs` from [WI-079](WI-079-diagnostic-bundle-coverage.md) | Copy the sandbox into a report-fixture script |
| Deliberate updates | Follow the SDK golden's `--check` and `--update` pattern | Rewrite expected files during normal tests |

WI-078 should test the sidecar's reader contract, not repeat the verifier. Keep the fixture fast and independent of user-data roots:

1. Render one failed sidecar and one passed-with-warnings sidecar.
2. Compare complete Markdown bytes.
3. Keep a few semantic checks for the meaning that must remain: verdict, causes, limits and next action.
4. Don't add exact terminal-output files yet. They duplicate existing CLI coverage and would make every prose edit a two-output migration.
5. Link a small, reviewed excerpt from `docs/VERIFICATION.md`. Keep complete generated files in the test fixture.
6. Add a deliberate `--update` command. Normal tests remain read-only.

The useful overlap with WI-079 is input construction and the sandbox only. WI-079 tests fault collection and CLI behavior. WI-078 tests the human report rendered from a structured result. Keep those responsibilities separate.
